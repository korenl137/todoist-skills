# Todoist 태스크 템플릿 가이드 v1.0

`todo-*` 스킬이 읽는 **작성 규칙 문서(`guide`)** 로 쓰기 위한 범용 템플릿이다.
설정 파일의 `guide`에 이 파일(또는 수정한 사본) 경로를 지정하면 스킬이 라벨을 붙이거나 점검하기 전에 읽는다.
설정 파일의 정의(`[labels.*]`, `[areas]`)와 이 문서가 어긋나면 **어긋남을 보고**하고, 사용자의 현재 결정이 우선한다.

목적: 사람이든 LLM/스킬이든 태스크를 추가·수정·갱신할 때 같은 형식을 유지한다.
구조: **코어 템플릿 1개** + **유형별 변형(코어와 다른 부분만)** + **갱신 규칙**.

---

## 0. 설계 원칙
1. **정보는 한 곳에만 둔다.** 같은 분류를 프로젝트·섹션·라벨·접두어에 중복하지 않는다. (공식: 프로젝트=어디, 라벨=교차 분류, 섹션=프로젝트 내부 단계)
2. **라벨은 적게.** 모든 태스크에 라벨을 붙일 필요가 없다. 걸러 볼 가치가 있는 것만.
3. **메타데이터가 이름보다 믿을 만하다.** 접두어는 사람이 읽는 용도, 필터·자동화는 라벨/우선순위/날짜로.
4. **완료 기준은 예/아니오로 판정 가능해야 하고, 증거가 남아야 한다.**
5. **단순하게.** 하위 구조는 얕게(공식 한도 4단계, 이 문서의 규칙은 2단계).

---

## 1. 코어 템플릿

### 1.1 제목
```
[유형·계열] 동사로 끝나는, 결과가 보이는 서술
```
- `유형`: §2의 고정 목록 중 하나. `계열`: 주제/프로젝트명, 선택, **8자 이내**, 세 번째 구획 금지.
- 접두어 뒤 본문은 **동사형**(일반 태스크) 또는 **결과 명사형**(상위 태스크). 모호한 명사 단독 금지.
  (나쁜 예: `GRC` / 좋은 예: `[조사] GRC follow-up 목록 갱신`)
- 상위 태스크의 결과 명사형 제목(예: `… 구축·검증`)은 **의도된 형식**이다. `todo-doctor`의 "모호한 제목" 판단에서 하위 태스크가 있는 상위 태스크는 이 규칙을 참고해 동사 없음을 이유로 지적하지 않는다.
- 진행 상태·날짜를 제목에 넣지 않는다.
- 길이: 목록에서 한눈에 읽히는 수준(권장 60자 이내). 하드 한도는 500자.
- 서식: 제목은 굵게/기울임/코드/링크/취소선만 가능.
- **제목에 `@`를 쓰지 않는다.** Todoist MCP로 태스크를 만들면 `@라벨`이 라벨로 파싱되어 제목에서 사라진다(실측). `{ } # %`, `p1`~`p4`, 날짜 단어는 이 경로에서 파싱되지 않고 글자 그대로 남았지만(실측), 앱의 Quick Add에서는 파싱될 수 있으므로 쓰지 않는다.
- 상위 태스크는 제목 끝에 ` (상위)`를 선택적으로 붙일 수 있다.

### 1.2 설명 (고정 순서, 빈 블록은 생략. ★는 필수)
```
> **유형** {유형} | **한 줄 요약** {한 문장} | **상태** {상태값}

## 목적 ★
왜 하는가. 1~3줄.

## 완료 기준 ★
예/아니오로 판정 가능한 문장. 산출물·측정값·결정 중 하나를 포함.

## 선행 / 입력
먼저 끝나야 할 것, 쓸 자료.

## 범위·제약
하지 않을 것, 승인이 필요한 행위(배포, 설정 변경 등).

## 절차
번호 목록. 5개 넘으면 하위 태스크로 분리.

## 근거·링크
출처 URL, 정본 경로. 내용은 복제하지 않고 위치만.

## 현재 상태 (YYYY-MM-DD)   ← 상위·장기 태스크에만. 한 곳에서 날짜와 함께 갱신.
```
- 서식 제한: 설명에서는 **H1·H2 헤딩**, 굵게/기울임, 글머리·번호 목록, 인용, 코드, 링크, 취소선만 쓴다. **H3 이하·표·체크박스는 쓰지 않는다.**
- 첫 줄 `> …`는 목록 화면에서 제목 바로 아래 미리보기로 보이므로 한 줄 요약을 가장 읽기 쉽게 쓴다.
- 길이: 하드 한도 약 16,383자(공식 문서 간 16,383/16,384 불일치). **권장 4,000자 이하.** 길어지는 날짜별 이력은 설명이 아니라 **댓글**(한도 15,000자)로 옮긴다.
- **설명 = 안정적인 기준 정보(목적·완료 기준·링크), 댓글 = 진행 경과·이력·첨부.**
- 필수(★)는 대화 맥락에서 도출한 **최소 문장**으로 채운다. 새 사실을 지어내지 않고, 도출할 수 없으면서 의미가 달라질 만큼 불확실할 때만 한 번 묻는다(스킬의 "빠진 것만으로 묻지 않는다"는 기본 동작과 맞춤).

### 1.3 상태값 (고정) 과 일관성 규칙
`미착수` · `진행` · `대기` · `보류` · `검증 대기`
- `대기`↔라벨 `waiting`, `보류`↔라벨 `on-hold`(이 라벨들을 설정에서 정의한 경우). 라벨이 붙어 있으면 헤더 상태가 일치해야 하며, 어긋나면 갱신 때 바로잡고 보고한다.
- **`waiting`/`on-hold`는 확인된 이유와 해제 조건을 설명에 한 줄 적을 때만** 붙인다(날짜 기반 추측 금지).
- `대기` 태스크는 due를 비운다(오늘/예정 화면 오염 방지). 주 1회 `waiting` 검토.

### 1.4 메타 필드
| 필드 | 규칙 |
|---|---|
| 프로젝트 | 주제가 아니라 **삶의 영역**(`[areas]`)으로 배치. 주제는 라벨로. |
| 우선순위 | 공식 의미를 따른다: **p1** 지금 처리(urgent+important, 동시 3개 이하 권장) / **p2** 중요, 일정 잡아 진행 / **p3** 덜 중요, 미뤄도 됨 / **p4** 기본값(우선순위 없음). **보류는 p4가 아니라 `on-hold` 라벨로 표시**한다. |
| 라벨 | §1.5 |
| 날짜 | `due` = 내가 이날 하겠다는 **계획일** / `deadline` = **넘기면 안 되는 마감**(외부 결과가 있을 때, Pro). 반복 태스크는 deadline 대신 반복 일정. 상위 태스크는 **due 없이 deadline만** 둔다(상위와 하위가 같은 날 due면 오늘 화면에 하위가 두 번 보임). |
| 계층 | 최대 **2단계**(상위→하위). 공식 한도는 4단계지만 얕게 유지. |
| 섹션 | 기본은 **사용하지 않음**(상태는 상태값/라벨이 담당하므로 섹션과 중복). |
| 반복 | `정비` 유형만. 절차는 설명에 쓰는 것이 기본. |
| 개수 | 하위는 상위당 10개 이하 권장. 프로젝트당 활성 태스크 한도 300. |

### 1.5 라벨
- 라벨은 **필터링 가치가 있을 때만** 붙인다. 정비·단순 실행·Inbox 태스크는 라벨이 없어도 정상이다.
- 설정의 `[labels.allowed]`/`[labels.projects]`에 **정의된 라벨만** 쓴다. 새 라벨 생성은 사용자 확인 후에만.
- 역할은 설정의 `[labels.roles]`를 따른다(action / project / topic / state). 권장 총 4개 이하(Todoist 한도: 태스크당 100개, 라벨명 60자, 계정 500개).
- 접두어(`act/` 등)가 붙은 구 라벨은 `[labels.retired]`로 새 라벨에 매핑하고, 새 태스크에는 쓰지 않는다.
- 아래 §2의 "행동 라벨" 열은 **기본 매핑 예**이며, 해당 라벨이 설정에 없으면 붙이지 않는다.

## 2. 유형(변형) — 코어와 다른 점만

| 유형 | 행동 라벨(예) | 추가·변경 블록 |
|---|---|---|
| **실행** | 없음 | 완료 기준 = 끝났음을 확인하는 행동 하나. 절차 생략 가능. 한 번에 끝나는 물리적 행동 단위. |
| **조사** | `review` | `## 질문`(1~3개), `## 산출물`(어디에 무엇을). 입력은 출처 링크. |
| **결정** | 없음(필요 시 `design`) | `## 선택지`, `## 판단 기준`. 완료 기준 = "A/B/C 중 하나로 결정하고 근거를 기록". |
| **제작** | `code` 또는 `design` | `## 변경 범위`, `## 검증`(테스트→시험→실사용 순). 승인 필요 행위를 범위·제약에 명시. |
| **실험** | `experiment` | `## 조건`(변수·값·고정 조건), `## 기록`(측정 항목·저장 위치), `## 판정 기준`. |
| **기록** | `write` | `## 대상 문서`, `## 갱신 항목`. 정본/요약 구분 필수. |
| **검토** | `review` | `## 검토 대상`, `## 판정 항목`. 완료 기준 = 판정과 근거 기록(수정은 별도 태스크). |
| **정비** | 없음 | **반복 일정 필수.** 목적·완료 기준 한 줄씩, 절차는 `A → B → C → 확인` 한 줄. |
| **행사** | 없음 | **deadline = 행사일 필수.** 하위는 deadline에서 역산한 due: 취합 → 핵심 선정 → 초안 → 점검 → 최종. |

- 유형 판정이 모호하면 묻는다. 한 태스크에 두 유형이 섞이면 **쪼갠다**.
- 기존에 쓰던 접두어(예: `[코드·X]`)는 가장 가까운 유형의 별칭으로 인정하고 일괄 개명하지 않는다.

### 2.1 정비 + 하위 체크리스트가 필요한 경우
기본은 설명에 절차를 쓴다. 매 주기마다 항목 체크가 꼭 필요하면 하위 태스크로 두되, Todoist의 **"하위 태스크 초기화(Reset sub-tasks)" 설정이 켜져 있어야** 다음 주기에 하위가 되돌아온다(최대 30개, 하위의 하위는 복원되지 않음).

## 3. 상위(Umbrella) 태스크
- 설명에는 **구조(하위 목록)·순서·정본 문서 입구·현재 상태(날짜)** 만. 상세는 정본 문서에 두고 복제하지 않는다.
- due 없음, 필요하면 deadline만. 하위가 모두 끝나도 상위의 `완료 기준`을 다시 확인한 뒤 완료.
- 우선순위는 활성 하위 중 가장 높은 것과 모순되지 않게(자동 변경하지 말고 불일치 시 보고).

## 4. Inbox 캡처 규칙
- 캡처는 형식 없이 OK: `링크/메모 + 한 줄 "무엇을 하려는지"`.
- 정리(분류) 시: 유형 결정 → 변형으로 제목·설명 채움 → 프로젝트 이동 → 필요한 라벨만.
- 정보가 부족하면 `대기` + 사용자에게 한꺼번에 질문. 정리 안 된 Inbox는 주 1회 처리.

---

## 5. 스킬/LLM 운영 규칙

### A. 추가 (`todo-add`)
1. 요청에서 **유형**을 판정(모호하면 질문). 2. 코어+변형으로 제목·설명·라벨·우선순위 구성.
3. ★ 필드는 대화 맥락에서 도출한 최소 문장으로 채운다. 새 사실을 지어내지 않고, 의미가 달라질 만큼 불확실할 때만 한 번 묻는다.
4. §1.4(2단계, 날짜 규칙)·§1.5(라벨) 검사 후 추가. 여러 개는 일괄 추가.
5. 추가 직후 읽기로 확인: 제목·설명이 의도대로 저장됐는지(특히 제목에서 파싱되어 사라진 부분이 없는지, 우선순위 값, 날짜).

### B. 수정 (`todo-update`, `todo-tidy`)
1. **읽기 먼저**(현재 설명·라벨·부모·날짜).
2. 설명은 **블록 단위로 갱신**, 바꾸지 않은 블록은 그대로 보존. 통째로 덮어쓰지 않는다. 원문 절차·링크는 글자 그대로 옮긴다.
3. `상태`(헤더)와 `## 현재 상태`는 함께, 날짜와 같이 갱신. 상태 라벨과 불일치하면 바로잡고 보고.
4. 이력을 남길 때는 **댓글**로(설명에 쌓지 않는다). 세션 요약 댓글은 요청이 있을 때만 남긴다.
5. 날짜 이동은 날짜만 바꾸는 경로(reschedule)로(반복 일정 보존). 기존 projectId/sectionId/parentId를 다시 보내지 않는다(이동으로 처리됨).
6. 유형을 바꾸면 접두어·행동 라벨·필수 블록을 함께 바꾸고 사용자에게 알린다.
7. **접촉 시 정합화**: 이미 수정하는 태스크에 한해 형식을 함께 맞춘다. 수정 요청이 없는 태스크는 건드리지 않는다.

### C. 완료 (`todo-complete`)
- `완료 기준`을 다시 읽고 **확인된 사실**이 있을 때만 완료. 증거(경로·링크·수치)를 완료 댓글 한 줄로 남긴다.
- LLM이 직접 수행했고 독립적으로 검증하지 못했으면 `검증 대기`로 두고 사람이 확인하게 한다.
- 반복 태스크는 완료만 하고 설명을 수정하지 않는다.

### D. 금지 (사용자 확인 없이는)
- 삭제(섹션을 지우면 안의 태스크도 함께 삭제됨), 프로젝트·섹션 구조 변경, 우선순위 일괄 변경, 프로젝트 이동, 새 라벨 생성.
- 승인이 필요한 행위(배포, 장비 실행, 설정 변경)를 설명에 "완료"로 적는 것. 존재하지 않는 근거 경로·링크를 쓰는 것.
- 소급 일괄 변환(§B-7 외).

### E. 주기 점검 (주 1회 권장)
`waiting` 라벨 검토 → Inbox 비우기 → 상태 라벨/헤더 불일치 점검 → p1 개수(≤3) 점검 → 설명 4,000자 초과 태스크의 이력을 댓글로 이전.
`todo-doctor`는 기본으로 Inbox를 점검 범위에서 제외하므로(정리 안 된 태스크는 아직 위반이 아님), **Inbox 비우기는 수동 또는 `todo-tidy`로** 한다. `todo-doctor`는 보고만 하고 고치지 않는다.

## 6. 예시

### 6.1 조사 (Inbox 링크 → 처리)
```
제목: [조사] 저장한 글이 소개하는 도구의 기능 파악
라벨: review | p4(기본)
```

## 7. 저장·배포 방식
- **정본은 이 문서(Git)**. Todoist 서버 도구로는 템플릿 목록 조회가 안 되고, 네이티브 프로젝트 템플릿(CSV)은 활성 태스크만 입출력하며 반복 일정이 바뀔 수 있어 유형 템플릿 저장소로 부적합하다.

## 9. 실측 결과와 미검증 항목
**실측 (2026-10-14, Todoist MCP `add-tasks`, 임시 태스크 생성 후 삭제):**
1. 제목 `[td-test] {deadline} #Personal @review %lbl p1 tomorrow …` → `@review`만 라벨로 파싱되어 제목에서 제거되었다. `{deadline}`, `#Personal`, `%lbl`, `p1`, `tomorrow`는 글자 그대로 남았고 날짜·프로젝트는 바뀌지 않았다.
2. 우선순위 `p1`을 보내면 `p1`로 저장·반환된다. 도구는 `p1`(최고)~`p4`(기본) 문자열을 쓰며, 정수는 받지 않는다.

**미검증:**
1. 앱의 Quick Add에서 `{ } # %`가 파싱되는지 (제목 규칙은 안전하게 금지 유지).
2. 도구의 `p1`이 앱 화면의 P1과 같은지: UI에서 만든 기본 태스크가 `p4`로 반환되는 것으로 방향은 정황상 일치하나, 화면 색으로 직접 확인하지는 않았다.
3. 설명 한도 16,383 vs 16,384 → 4,000자 권장으로 영향 없음.
4. 스킬이 이 가이드를 실제로 읽고 따르는 실행(end to end): 다음 세션에서 스킬을 설치한 환경에서 `todo-add`로 태스크를 만들어 확인해야 한다.

## 10. 스킬 연결 점검 (정적, 2026-10-15)
`SKILL.md` 원문을 가이드와 대조했다. 실행 테스트가 아니라 문서 간 비교다.

| 스킬 | `guide` 읽기 | 가이드와 맞춘 점 |
|---|---|---|
| `todo-add` | 설정 파일에 `guide`가 있으면 읽는다("Settings" 절) | ★ 블록을 맥락에서 채우고 의미가 달라질 때만 묻는다("빠진 것만으로 묻지 않는다"). 상태 라벨에 이유·해제 조건을 설명에 적는다. 하위 태스크에 부모 라벨을 복사하지 않는다. |
| `todo-update` | 같음 | 읽고 나서 변경 필드만 보낸다. 기존 형식과 무관한 내용을 보존한다. 날짜만 바꾸면 reschedule을 쓴다. 세션 요약 댓글은 요청 시에만 남긴다. |
| `todo-doctor` | 같음. 가이드와 설정의 불일치를 발견으로 보고한다 | Inbox는 점검 범위에서 제외된다(§5-E). 보고만 하고 고치지 않는다. |

남은 위험: `todo-doctor`가 설정에 정의되지 않은 라벨(예: 가이드가 예시로 든 `review`, `experiment`)을 "가이드와 설정의 불일치"로 보고할 수 있다. 사용 전에 설정의 `[labels.allowed]`에 쓰는 라벨을 정의해 두면 줄어든다.
